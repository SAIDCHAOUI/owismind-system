## Run 1 : mode Claude bascule sur Sonnet 5 (incident sous-agents resolu, VALIDE webapp)

### Objectif
Remplacer Claude Sonnet 4.6 par Claude Sonnet 5 comme modele du tier "claude" (plus recent,
moins cher). Symptome initial : l'orchestrateur repondait en Sonnet 5 mais les sous-agents
echouaient ("souci technique") uniquement en mode claude via la webapp, alors qu'ils
semblaient marcher testes seuls.

### Fait
- Diagnostic complet du chemin mode claude : front (mode logique) -> backend python-lib
  (AUCUN id de modele, transmet le mode en token de controle) -> orchestrateur
  (`LOOP_LLM_BY_MODE`, SA copie de `SONNET_ID` L72) -> message systeme `MODE: claude` injecte
  au sous-agent -> sous-agent (`forced_mode` + `pick_subagent_llm`, SA PROPRE copie de
  `SONNET_ID` L70/L76) -> tool Semantic Model Query (modele configure dans DSS, hors code).
- Faux positif de test explique : sans contexte injecte, un sous-agent teste stand-alone
  tourne en `DEFAULT_MODE=smart` (Gemini) : le chemin claude n'etait jamais exerce. Recette
  fiable : `DEFAULT_MODE="claude"` temporaire + Quick test (puis remettre smart).
- Cause racine (logs analyses par l'IA interne + notebook) : la case "Reasoning Model" de
  l'entree `vertex_ai/claude-sonnet-5` (connexion `LLM-7064-revforecast`) fait envoyer
  `reasoning_effort` par DSS ; le proxy LiteLLM le traduit en ancien dialecte
  `thinking: {type: "enabled"}` sur le chemin `response_format` (JSON force) alors que la
  famille Claude 5 exige `thinking.type.adaptive` + `output_config.effort` -> HTTP 400.
  Seul `with_json_output` cassait : orchestrateur OK (jamais de JSON force en boucle,
  L056), sous-agents KO (UNDERSTAND force le JSON), et seulement en mode claude
  (smart/pro = Gemini, qui accepte).
- Matrice notebook (user) : decoche = plain OK + json OK ; Standard / Custom low = plain OK
  + json 400 `thinking.type.enabled` ; Custom "adaptative" = 400 partout (`Invalid
  reasoning_effort`, valeurs proxy : minimal/low/medium/high/xhigh/max/none).
- Fix applique (DSS, user) : case "Reasoning Model" DECOCHEE sur l'entree sonnet-5. Famille
  Claude 5 : aucun parametre thinking = thinking ADAPTATIF actif par defaut (effort defaut
  high). Rien de perdu sauf le reglage fin d'effort (reviendra via ticket plateforme).
- Bench de validation (mesh vs LiteLLM direct, 3 prompts calcul, 24 appels) : 24/24 justes ;
  mesh decoche == direct sans parametre ; modulation adaptative visible (~200 tokens prompts
  simples vs ~1384 sur le dur) ; preuve du thinking silencieux sur "piege" (reponse ~10
  tokens visibles, completion ~84).
- Repo aligne : `claude-sonnet-4-6` -> `claude-sonnet-5` dans 12 fichiers hors tests
  (3 Code Agents, `owismind_factory/{hub,tool_builder,guided}.py`,
  `owismind_hub/factory_settings.json`, `Notebooks/01_push_config_hub.py`, CLAUDE.md dev,
  PLAYBOOK_ADD_AGENT.md, semantic-models README.md + MODEL.md). 741 tests verts, 0
  occurrence restante hors tests.
- Bombe a retardement identifiee (couverte par le fix) : le planner durable et le correlate
  de l'orchestrateur utilisent aussi `with_json_output` (correlate en tier Sonnet dans TOUS
  les modes, `CORRELATE_LLM_MODE="claude"`) : auraient casse a l'activation du flag durable
  si la case etait restee cochee.
