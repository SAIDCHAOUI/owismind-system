## run 1 : tableaux de resultat agent, pagination du resultat COMPLET + compteur honnete

**Objectif** : retour terrain user. Dans Evidence (onglet Preuves, section resultat) et l'onglet
Tableau, une requete de l'agent renvoyant > 1000 lignes s'affichait tronquee a 50 lignes avec
"50 lignes" comme total : impossible pour un utilisateur metier de savoir que le resultat etait
partiel. Demande : afficher 100 lignes, dire "100 sur 1000", scroll qui charge la suite comme
Source Data.

**Cause racine** : les 3 Code Agents (orchestrateur + 2 sous-agents) capent le resultat capture
a `MAX_RESULT_ROWS = 50`, et leur `row_count` est calcule APRES la coupe
(`extract_semantic_payload` : `len(found["rows"])` ; moteur direct : fetch `max_rows + 1`).
Le vrai total n'existait nulle part. Le flag `truncated` etait bien pose, mais l'UI ne disait
que "Resultat tronque - premieres lignes seulement" a cote de "50 ligne(s)".

  validateur `validate_evidence_result_rows_request` (limit/offset clampes comme /evidence/rows) ;

## run 1 (suite) : durcissement de la garde de relance apres revue de securite automatique

La revue de securite du commit `84a1cde` a signale des contournements de `check_rerunnable_select`
(details partiels recus : "sql-injection / authorization bypass", "denylist-incomplete",
"sql-gate-bypass"). Confirmes et corriges :
- La garde reutilisait `_scan_scopes` (parseur best-effort d'affichage) qui laisse OPAQUES les
  groupes non-SELECT : `COALESCE((SELECT x FROM secret), 0)` ou `((SELECT ...))` lisaient une
  table hors projet sans controle. Remplace par `_relation_sites` : balayage PLAT de tous les
  jetons, a toute profondeur (FROM/JOIN/virgule de liste FROM par niveau de parenthese ; FROM
  d'EXTRACT/SUBSTRING/TRIM/OVERLAY/POSITION et IS DISTINCT FROM exclus).
- Ombre de CTE : `WITH secret AS (SELECT * FROM secret)` masquait la vraie table. Desormais un
  seul WITH de tete (pas de WITH imbrique, pas de RECURSIVE) et un nom de CTE ne masque une
  relation que dans la requete principale ou le corps d'une CTE POSTERIEURE.
- Liste noire de fonctions incomplete par nature : remplacee par une LISTE BLANCHE
  (`_SAFE_FUNCTIONS` + mots-cles avant parenthese) ; appel qualifie par schema, UDF, fonction
  executant du SQL texte (table_to_xml, ts_stat...) et `(TABLE x)` refuses.
- Effet en cas de refus : la relance echoue proprement, l'UI garde l'extrait avec la phrase honnete.
Tests : 1037 plugin verts (+5 tests de contournement). Zip DEV regenere. Commit local (non pousse).
Le "+1 more" de la 1re alerte n'a pas ete recu en detail : a recouper si la revue est relancee.

## run 1 (suite 2) : verification AUTORITATIVE par le plan PostgreSQL

Nouvelle alerte de revue ("parser-differential / authorization bypass", "allowlist bypass").
Confirme : toute grammaire SQL ecrite a la main peut lire une requete autrement que PostgreSQL
(ex. jointure parenthesee `FROM (secret CROSS JOIN t)` : `secret` invisible au balayage de jetons ;
appel en notation attribut `t.ma_fonction` sans parentheses). Correctif : `evidence/plan_guard.py`
(pur) + `service._assert_plan_safe` : avant chaque relance, `EXPLAIN (FORMAT JSON, VERBOSE)` de la
requete EXACTE enveloppee (planifiee, jamais executee) ; refus si une relation scannee n'est pas un
dataset decouvert (correspondance EXACTE nom + schema, `strict_relation_matcher`), si un noeud est
Function/Table Function/Tuplestore/Foreign/Custom/Sample Scan, ou si une fonction deparsee dans une
expression n'est pas dans `sql_parse.SAFE_FUNCTIONS` (+ noms de deparse/mots-cles ; qualifie
seulement `pg_catalog`). Echec de l'EXPLAIN = refus (fail closed). La garde par jetons reste en
premier filtre. Tests : 1046 plugin verts (+9 plan_guard). Zip DEV regenere (19h24).
Risque assume : faux refus possibles (fonction legitime absente de la liste, forme de deparse
inattendue) -> extrait + phrase honnete ; motif visible dans les logs `plan refused`.
